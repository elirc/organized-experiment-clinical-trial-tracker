# Architecture Overview

This project is a Next.js + TypeScript clinical trial participant tracking system with a backend-centered design. The key domain rules are: participants move through screening, enrollment, visits, deviations, adverse events, and study completion; protocol versions are immutable and append-only in [prisma/schema.prisma](/c:/Users/Owner/Desktop/ww11/prisma/schema.prisma); and visit schedules are generated from `enrolledAt` in [src/lib/domain/protocolRules.ts](/c:/Users/Owner/Desktop/ww11/src/lib/domain/protocolRules.ts), not from the current calendar or active protocol version.

The top-level folders map to explicit layers:

- `src/app`: Next.js pages and REST route handlers. For example, [src/app/api/participants/route.ts](/c:/Users/Owner/Desktop/ww11/src/app/api/participants/route.ts) is the HTTP entry point for listing and creating participants, while [src/app/participants/[participantId]/page.tsx](/c:/Users/Owner/Desktop/ww11/src/app/participants/[participantId]/page.tsx) renders the participant detail screen.
- `src/services`: Business logic and lifecycle orchestration. [src/services/participantService.ts](/c:/Users/Owner/Desktop/ww11/src/services/participantService.ts) owns enrollment and study completion, [src/services/visitService.ts](/c:/Users/Owner/Desktop/ww11/src/services/visitService.ts) owns visit completion, and [src/services/protocolService.ts](/c:/Users/Owner/Desktop/ww11/src/services/protocolService.ts) owns version creation and activation.
- `src/repositories`: Persistence seams. [src/repositories/participantRepository.ts](/c:/Users/Owner/Desktop/ww11/src/repositories/participantRepository.ts) scopes reads by site access, [src/repositories/protocolRepository.ts](/c:/Users/Owner/Desktop/ww11/src/repositories/protocolRepository.ts) handles active-version activation/retirement, and [src/repositories/auditRepository.ts](/c:/Users/Owner/Desktop/ww11/src/repositories/auditRepository.ts) appends immutable audit events.
- `src/lib`: Cross-cutting infrastructure and domain rules. Auth lives in [src/lib/auth/session.ts](/c:/Users/Owner/Desktop/ww11/src/lib/auth/session.ts) and [src/lib/auth/permissions.ts](/c:/Users/Owner/Desktop/ww11/src/lib/auth/permissions.ts), request guards live in [src/lib/http/routeContext.ts](/c:/Users/Owner/Desktop/ww11/src/lib/http/routeContext.ts), lifecycle rules live in [src/lib/domain/stateTransitions.ts](/c:/Users/Owner/Desktop/ww11/src/lib/domain/stateTransitions.ts), and Zod schemas live under [src/lib/validation](/c:/Users/Owner/Desktop/ww11/src/lib/validation).
- `src/hooks` and `src/components`: Thin frontend integration. [src/hooks/useParticipants.ts](/c:/Users/Owner/Desktop/ww11/src/hooks/useParticipants.ts) and [src/hooks/useParticipantDetail.ts](/c:/Users/Owner/Desktop/ww11/src/hooks/useParticipantDetail.ts) call the REST API, while [src/components/dashboard/ParticipantDashboard.tsx](/c:/Users/Owner/Desktop/ww11/src/components/dashboard/ParticipantDashboard.tsx) and [src/components/participants/ParticipantDetailView.tsx](/c:/Users/Owner/Desktop/ww11/src/components/participants/ParticipantDetailView.tsx) render results without owning domain rules.
- `prisma`: Canonical schema design. Even though this learning build uses mock-backed repositories from [src/lib/mock-db/store.ts](/c:/Users/Owner/Desktop/ww11/src/lib/mock-db/store.ts), the intended relational model is fully described in [prisma/schema.prisma](/c:/Users/Owner/Desktop/ww11/prisma/schema.prisma).
- `tests`: Focused architecture tests. The most important behaviors are covered in [tests/services/permission-enforcement.test.ts](/c:/Users/Owner/Desktop/ww11/tests/services/permission-enforcement.test.ts), [tests/validation/participantSchemas.test.ts](/c:/Users/Owner/Desktop/ww11/tests/validation/participantSchemas.test.ts), [tests/services/participant-transitions.test.ts](/c:/Users/Owner/Desktop/ww11/tests/services/participant-transitions.test.ts), and [tests/services/site-scoping.test.ts](/c:/Users/Owner/Desktop/ww11/tests/services/site-scoping.test.ts).

The stack choice is intentional:

- `Next.js + React` for a realistic internal CRUD product shell.
- `TypeScript` for shared contracts in [src/types/domain.ts](/c:/Users/Owner/Desktop/ww11/src/types/domain.ts).
- `PostgreSQL + Prisma` as the production persistence target because the model is relational and transaction-heavy.
- `Zod` for explicit validation in [src/lib/validation/participantSchemas.ts](/c:/Users/Owner/Desktop/ww11/src/lib/validation/participantSchemas.ts), [src/lib/validation/protocolSchemas.ts](/c:/Users/Owner/Desktop/ww11/src/lib/validation/protocolSchemas.ts), [src/lib/validation/visitSchemas.ts](/c:/Users/Owner/Desktop/ww11/src/lib/validation/visitSchemas.ts), and [src/lib/validation/eventSchemas.ts](/c:/Users/Owner/Desktop/ww11/src/lib/validation/eventSchemas.ts).
- `React Query` for thin data hooks in [src/hooks/useParticipants.ts](/c:/Users/Owner/Desktop/ww11/src/hooks/useParticipants.ts) and [src/hooks/useParticipantDetail.ts](/c:/Users/Owner/Desktop/ww11/src/hooks/useParticipantDetail.ts).
- `REST` instead of tRPC because route handlers, validation boundaries, permission guards, and service seams are easier to trace explicitly for learning in [docs/architecture/request-lifecycle.md](/c:/Users/Owner/Desktop/ww11/docs/architecture/request-lifecycle.md).

Multi-tenancy is intentionally not included. The product reads as a single sponsor-operated system, so the code uses site-level scoping instead: session scope is computed in [src/lib/auth/session.ts](/c:/Users/Owner/Desktop/ww11/src/lib/auth/session.ts) and enforced in [src/repositories/participantRepository.ts](/c:/Users/Owner/Desktop/ww11/src/repositories/participantRepository.ts). The changes needed to add true tenant isolation are documented in [docs/architecture/auth-and-permissions.md](/c:/Users/Owner/Desktop/ww11/docs/architecture/auth-and-permissions.md).
